Types, Schemas, and Constraints

Chapter 16Constraints

This chapter formalizes integrity constraints for property graphs in GQL and explains how they interact with the underlying typing discipline. We begin with key and uniqueness constraints based on constraint graph patterns, and then describe their enforcement during updates and transactions. Finally, we connect these dynamic checks to a lightweight effect system, which approximates write footprints and write conflicts without claiming to determine evaluation-order or context dependence, or result determinism.

16.1 Keys and Uniqueness

Recall from Section 15.3 that a key label set identifies a keyed node or edge type in a graph type and is not itself an integrity constraint.

Remark (scope as a graph pattern). The scope of a constraint is a deterministic constraint graph pattern P introduced by FOR. Its main element variable identifies the constrained node or edge; an edge scope also declares its endpoint variables.

Key specifications. A key or unique specification is a tuple

χ = ⟨P,c¯⟩,

where c¯ = ⟨c1,… ⁡,cn⟩ is a sequence of n ≥ 0 key value components. A component is the main element variable, an endpoint variable of an edge scope, or a property reference rooted at one of those variables. For a binding b matched by P, let

tχ(b) = ⟨⟦c1⟧b,… ⁡,⟦cn⟧b⟩.

Property references use the expression semantics of GQL: an absent property yields null when the declared result type is nullable, and otherwise raises the prescribed data exception. Thus absent never becomes a key value component.

Non-distinctness (for KEY and UNIQUE). Write a ≈ b when a and b are not distinct under GQL’s recursive value-comparison rules, and lift this relation pointwise to key tuples:

⟨ai⟩i ≈⟨bi⟩iiff∀ ⁡i.ai ≈ bi.

In particular, two null values are non-distinct; the rule also applies recursively to composite supported property values.

Constraint-scope notation. For a deterministic constraint graph pattern P, let matchG(P) be the set of bindings in its match result over G, with multiplicities ignored. For b ∈matchG(P), main(b) is the graph element bound to the main element variable of P. The predicate nullContaining(v) holds exactly when v is the null value or is a composite value having a recursively null-containing component.

Key constraint (KEY). A graph G satisfies KEY(χ) iff every key tuple is not null-containing and any two constrained elements with non-distinct key tuples are identical:

∀ ⁡b ∈matchG(P).¬ ⁡nullContaining(tχ(b)), ∀ ⁡b1,b2 ∈matchG(P).tχ(b1) ≈tχ(b2) ⇒main(b1) = main(b2).

Null-containment is recursive, so a composite component containing the null value also violates the key constraint.

Uniqueness constraint (UNIQUE). A graph G satisfies UNIQUE(χ) iff any two constrained elements with non-distinct key tuples are identical:

∀ ⁡b1,b2 ∈matchG(P).tχ(b1) ≈tχ(b2) ⇒main(b1) = main(b2).

No separate null-containment test is performed for UNIQUE. When n = 0, all empty key tuples compare alike, so either form permits at most one constrained element.

Example: BookHasKey. The BookHasKey declaration in Section 4.2 has the key specification

PBook = (b:Book),c¯Book = ⟨b.isbn⟩,χBook = ⟨PBook,c¯Book⟩.

For the bindings β1 and β2 produced by this constraint pattern for the two book nodes in the library example,

tχ Book(β1) = ⟨’978-83-123...’⟩, tχ Book(β2) = ⟨’978-83-987...’⟩.

Both tuples are non-null-containing and they are unequal, so the two book nodes satisfy the KEY requirement. If two bindings for distinct book nodes instead produced the same non-null ISBN tuple, then main(β1)≠main(β2) would violate KEY(χBook). Under a hypothetical UNIQUE declaration with the same specification, equal ISBN tuples would be non-distinct and would likewise require the main elements to be identical; unlike KEY, UNIQUE performs no separate null-containment test.

General constraint specifications. Let CDesc be the disjoint union of the carriers of key-constraint and unique-constraint descriptors. Every constraint defined by this edition is of exactly one of those two kinds. Its descriptor contains its name, registered-subject set, deterministic scope, and key value component specification. Constraints in a graph type apply to all graphs registered as subjects of that graph type; constraints defined in a graph apply only to that graph. Concrete examples are shown in Section 4.2.

For each constraint body C, let CBNF(C) be the implementation-defined, deterministic and idempotent normal form representing its equivalence class. Two bodies are body-equivalent exactly when their normal forms are equal; equivalence accounts for both equivalent constraint scopes and equivalent key value component specifications. The analogous normal form CSNF for a constraint specification also retains its constraint name. These normal forms determine the scope and requirement information represented in constraint descriptors.

Syntactic form of constraint specifications. Constraint specifications occur as CONSTRAINT body items of a nested graph type specification and in standalone constraint-management statements:

BNF
graph-type-body-item ::= ... | "CONSTRAINT" constraint-spec
constraint-spec ::= constraint-name constraint-body
constraint-body ::= "FOR" constraint-graph-pattern
                    "REQUIRE" constraint-requirement
constraint-requirement ::= key-value-spec "IS" "KEY"
                         | key-value-spec "IS" "UNIQUE"
key-value-spec ::= key-value-component
                 | "(" [ key-value-component-list ] ")"
key-value-component-list ::= key-value-component
                             { "," key-value-component }
key-value-component ::= element-variable [ "." property-name ]

create-constraint-stmt ::=
  "CREATE" ( "CONSTRAINT" [ "IF" "NOT" "EXISTS" ]
             | "OR" "REPLACE" "CONSTRAINT" )
  [ constraint-parent-graph-spec ] constraint-spec

drop-constraint-stmt ::= "DROP" "CONSTRAINT" [ "IF" "EXISTS" ]
                         [ constraint-parent-graph-spec ] constraint-name

constraint-parent-graph-spec ::= graph-expression "."

If the parent graph specification is omitted, CURRENT_GRAPH is implicit. Let IG be the selected graph’s direct constraint dictionary and, when it has a constraining graph type, let IGT be that type’s constraint dictionary. Constraint names are unique independently of origin, so their domains are disjoint. A plain CREATE CONSTRAINT using a name already in IG raises G1004; without IF NOT EXISTS, a name already in IGT is not permitted. If the new body is body-equivalent to a constraint in either dictionary and IF NOT EXISTS is absent, creation raises G1006. With IF NOT EXISTS, an existing name or a body-equivalent constraint in either dictionary makes the statement a no-op. OR REPLACE can replace only a same-named constraint in IG; it cannot replace an inherited constraint, and the body-equivalence rule still applies. Otherwise, creation validates the constraint against the selected graph before adding it to IG; dropping removes a direct constraint from that dictionary. An inherited constraint cannot be dropped in this way.

16.2 Constraint Enforcement and Effects

Graph-type conformance Σtyping. For an optional constraining graph-type reference, define Σtyping(GT?) as follows. When GT? = GT, it is the clause requiring every node and edge to be of a node or edge type specified by the resolved graph type, including exact label/property sets, property value types, directionality, and endpoint node types, and requiring every constraint of that graph type to be satisfied. Failure means that the graph is no longer of its constraining graph type and is reported as graph type violation G2000. For GT? = none the component is empty.

Direct graph constraints and graph-type conformance. Let GE = ⟨G,GT?,I G⟩ be the active graph entry. Its direct constraint set is

Idirect(GE) = ran(IG).

The derived set Iactive(GE) from Section 15.5 remains useful when referring collectively to every constraint registered for the graph, but validation retains the two origins: graph-type constraints are part of the graph-type-conformance test, while Idirect is validated directly. Define

⟦GE⟧ = Σtyping(GT?) ∪I direct(GE).

The first component is empty for an open graph and otherwise states that the graph is of its constraining graph type, including satisfaction of that graph type’s constraints. The second contains the key or unique constraints defined directly on this graph. No declaration from an unrelated graph entry or graph type is consulted.

Satisfaction of a constraint set. Each semantic clause σ ∈⟦GE⟧ has a satisfaction relation G⊧σ. For any set of clauses S, write

G⊧Siff∀ ⁡σ ∈ S.G⊧σ.

This is the meaning of the satisfaction test used by the enforcement below. The effect of these checks on insertion, update, and deletion is illustrated in Section 4.3.

Key and uniqueness constraints. Every descriptor in Iactive(GE) contributes exactly the KEY(χ) or UNIQUE(χ) clause described in Section 16.1. This uses the descriptor’s deterministic constraint graph pattern as scope and retains its complete key value component sequence; it is not reduced to a global label/property dictionary.

Validation predicate. For an active graph entry GE with pre-state graph G and a coalesced update delta Δ, define

okGE(G,Δ)iffG ⊕Δ is defined and (G ⊕Δ)⊧⟦GE⟧.

Constraint enforcement. After a primitive data-modifying statement has produced its provisional graph, every constraint in Idirect(GE) is dynamically validated by that statement’s General Rules; failure raises integrity constraint violation (23000). The separate graph-type-conformance test also checks the structural requirements and every constraint of the resolved graph type; failure raises graph type violation G2000. The statement cannot complete successfully while either validation fails.

16.3 Effect System and Write-Purity

The following informative effect system is defined only for query statements and data-modifying statements. Catalog-modifying statements are outside its domain and retain their statement-specific rules.

Here Σ is the applicable static graph-type descriptor and T is a finite typing environment for binding variables. For X ∈{V,E}, let TX be the restriction of T to variables whose declared graph-element reference type has kind X; membership of a variable in TX abbreviates membership in the domain of that restricted environment. The carrier of static effects is written 𝔈, so it is distinct from the typing environment. Effects form a commutative idempotent monoid (𝔈,⊔eff, ∅), where ⊔eff combines effects and ∅ denotes the absence of effects.

Let P range over read parts, S over query or data-modifying statements, a over primitive update-action templates, U over finite write parts composed of such templates, T′ over output typing environments, and 𝜀eff ∈𝔈. The rules below use two auxiliary static judgments:

Σ; T ⊢ P ⇒T′andΣ; T ⊢ aok.

The first holds when the read part P is well typed under Σ and T, producing the extended environment T′. The second holds when every target and embedded expression of the action template a is well typed in the given environment. For a write part U, fv(U) is the set of binding variables occurring free in its action templates.

We use the following effect-oriented judgments:

Σ; T ⊢ U : 𝜀eff(write-part templates have static effect 𝜀eff)
Σ; T ⊢ S : 𝜀eff(query or data-modifying statements have static effect 𝜀eff)

The static effect 𝜀eff is a conservative description, derived without executing the statement, of the kinds of state changes that the evaluated construct may perform. A statement is write-pure in this effect model iff its static effect is empty, that is, iff 𝜀eff = ∅. This says only that the statement has no modeled graph-data write. It does not imply that evaluated expressions are deterministic, exception-free, independent of evaluation order, or independent of observable context.

These constructors are not user syntax; they are meta-level names for the store-level steps that realize the write part U. Where we use schematic typing-level actions such as Create⟨⋅⟩, they are understood as abstracting the same runtime updates that are ultimately lowered to the corresponding insNode or insEdge actions.

Primitive effects and algebra. For static analysis, each primitive update action is abstracted by a primitive effect that records its write footprint while omitting runtime-specific information such as element identities, endpoint identities, and computed property values. We model these effects by a small set of constructors used in the meta-language.

Parameters range over vertex-label sets ΛV ⊆ 𝕃, edge-label sets ΛE ⊆ 𝕃, property keys k ∈ 𝕂, element kinds X ∈{V,E}, and labels ℓ ∈ 𝕃. The symbol ⊤ ⁡Λ denotes an implementation-agnostic “unknown or unconstrained” label-set abstraction.

eeff ::= CreateV[ΛV ]∣DeleteV[ΛV ]∣CreateE[ΛE]∣DeleteE[ΛE] ∣Set(X,k)∣ClearProps(X)∣RemProp(X,k) ∣AddLbl(X,ℓ)∣RemLbl(X,ℓ)(X ∈{V,E}).

The effect combination introduced above is commutative, so the order in which effects are combined is irrelevant, while idempotence means that recording the same effect more than once does not change the combined effect.

We write eeff,1 ≤effeeff,2 when eeff,2 is a less specific abstraction of eeff,1; for example,

CreateV[ΛV ] ≤effCreateV[⊤ ⁡Λ].

The join operator is monotone with respect to this order. In particular, for every finite family of effects, if eeff,i ≤effeeff,i′ for each i ∈{1,… ⁡,n}, then

⊔ eff ⁡ i=1ne eff,i ≤eff ⊔ eff ⁡ i=1ne eff,i′.

Thus, replacing any component effect by a less specific abstraction yields a correspondingly less specific abstraction of the combined effect.

Static conflict approximation and ordering constraints Let MayConflict be a symmetric predicate on pairs of effects. It holds for 𝜀eff,1 and 𝜀eff,2 if

Null assignment and property removal. A SET property item performs store assignment to the property’s declared type. The null value is therefore stored only when that type is nullable; otherwise it is not assignable and the prescribed error is raised. Assigning null is never lowered to property removal. Property removal is a separate data-modifying operation expressed by REMOVE.

Effect soundness (informative) Let 𝜀eff,S be the static effect of S and let Δ be the coalesced sequence of primitive actions produced at runtime. Every primitive action in Δ refines some eeff ∈ 𝜀eff,S under ≤eff. This establishes soundness only for the write-footprint abstraction. A rewrite cannot be justified from 𝜀eff,S alone: it must separately preserve evaluation order, exceptions, result bags, context-dependent expression behavior, and all other observable behavior.

Micro-derivation: write-purity of query-only statements (informative) If S has no write part (i.e. S ≡ P with result production only), then Σ; T ⊢ S : ∅. Therefore S performs no writes described by this effect algebra. Reordering or common-subexpression elimination additionally requires the relevant expressions to be independent of the changed evaluation order and context, to preserve exception behavior, and to preserve the result bag.

Constraint-Preserving Execution Recall the graph-entry validation set ⟦GE⟧ and validation predicate okGE(G,Δ) from the previous section. An execution of a data-modifying statement within a transaction, with pre-state G and coalesced delta Δ, is constraint-preserving if okGE(G,Δ) holds, that is, if the post-state G ⊕Δ satisfies its constraining graph type and all key/unique constraints defined directly on that graph. The operational semantics of DML rejects a structural graph-type violation or a violation of any direct graph constraint. Thus a primitive data-modifying statement completes successfully only if its post-state is constraint-preserving. Catalog-modifying statements are not modeled as G ⊕Δ; each uses the checks specified by its own Syntax and General Rules.

Chapter 16 — Takeaways.
  • Purpose: Formalized integrity constraints and their interaction with typing and updates.
  • Introduced: Key and uniqueness constraints over graph elements; enforcement rules and violation outcomes; an effect-based approximation of statement footprints to reason about potential conflicts.
  • Key distinctions: Key constraints (identification) versus uniqueness constraints (non-duplication without identification semantics); static approximations of effects versus data-dependent, dynamic effects.
  • Consequences: Determined when and how violations were detected and what observable outcomes followed; enabled reasoning about write footprints without conflating them with evaluation-order or context dependence; connected statement completion to dynamic constraint validation.
  • Bridge: Required a precise catalog and session model so that names, schemas, and constraints could be resolved consistently at runtime.
